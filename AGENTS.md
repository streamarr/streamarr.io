# streamarr.io - Project Guidelines

The marketing site for Streamarr, in two packages with separate lockfiles: `cms/` (Payload 4 beta on
TanStack Start, Postgres) and `site/` (TanStack Start, prerendered to static files). Run npm inside
the package you are changing.

## Commands
- `nvm use` first: the CMS needs Node 24.22.1 or newer, and both packages set `engine-strict`.
- `docker compose up -d --wait` (repo root) starts the CMS's Postgres on `127.0.0.1:5442`.
- `cms/`: copy `.env.example` to `.env` once. `npm run dev` serves the admin at
  `localhost:3000/admin` and GraphQL at `/api/graphql`. `npm run seed` writes the placeholder pages.
  `npm run test:int` needs the database.
- `site/`: `npm run dev` (port 3001) reads pages live from the CMS. `npm run build` prerenders every
  page reachable from `/` and needs the CMS running; a link to a site path that does not exist fails
  it. `npm test` runs Vitest; one file: `npx vitest run src/blocks/Blocks.test.tsx`.
- After changing a collection or a block, run `npm run schema` in `cms/`, then `npm run codegen` in
  `site/`, and commit both outputs. `schema:check` and `codegen:check` are the CI drift gates.
- CI (`.github/workflows/ci.yml`) runs the site checks, the CMS checks, and a job that seeds a CMS
  and prerenders the site from it. `build` is the required check.

## Engineering Philosophy

### Pre-production
Nothing is deployed. Change the content model and the site in place; delete a retired block or field
rather than keeping an adapter for it.

### TDD: Red-Green-Refactor
Write the failing test first, make it pass with the simplest change, refactor only while green. A
defect starts with a test that reproduces it.

### Root Cause First
Reproduce a bug and state its mechanism before fixing it. Fix it in the layer where the mechanism
lives, and state the root cause in the pull request.

### Tidy First
A commit is either structural (rearranging without changing behavior) or behavioral, and structural
changes come first when a task needs both.

### Commit Discipline
- Commit subjects start with lowercase `structural:` or `behavioral:`. Messages stay under 200 words.
- Sign every commit (`git commit -S`).
- Commits, pull requests and issues carry the author's words only: no Co-Authored-By trailers,
  "Generated by" lines or any other AI attribution.
- Commit only when format, types and tests pass.

### Code Style
- Prettier decides formatting in `site/` (no semicolons, single quotes, 100 columns).
- Early returns and guard clauses; route on `__typename` or another discriminant with one return per
  member.
- TypeScript is strict with no `any`: type unknown input as `unknown` and narrow it. Named exports
  only, except where a tool requires a default. `import type` for types.
- Build stateful modules as factories that take collaborators in one dependencies object
  (`createCmsClient({ fetch, url })`), so tests pass fakes instead of mocking modules.
- Comments explain a non-obvious contract or why code must be unusual.

## Architecture Rules
- **The published site is static.** A visitor's browser never contacts the CMS, which may be
  offline. Every CMS read lives in a server function whose last middleware is
  `staticFunctionMiddleware` (`site/src/cms/page.ts`): the build runs it and saves the answer beside
  the page.
- **Server-only values stay inside handlers.** Module scope is bundled for the browser too, so read
  `process.env` and build the CMS client inside the server function's handler.
- **GraphQL documents are build-time strings.** They live in `.graphql` files beside their feature
  and compile to typed strings (`documentMode: 'string'`); the browser ships no GraphQL client.
- **One fragment and one component per block.** `Page.layout` is the GraphQL union `Page_Layout`.
  A block gets a fragment on its type, a component that takes that fragment, a spread in
  `site/src/pages/page.graphql`, and a case in `site/src/blocks/Blocks.tsx`. A block type the site
  does not know renders nothing, so the CMS can gain a block before the site handles it.
- **Blocks share field names only when the types agree.** A field name used by several blocks must
  have the same type and nullability in each, or every query has to alias it.
- **Links an editor typed go through `CmsLink`**, which sends site paths through the router and
  leaves other addresses as ordinary links.
- **Generated files change only through their generator**: `cms/schema.graphql`,
  `cms/src/payload-types.ts`, `cms/src/routeTree.gen.ts`, `cms/src/app/_payload/importMap.js`,
  `site/src/graphql/generated/`, `site/src/routeTree.gen.ts`.

## Payload 4 beta
- For Payload work, read `cms/node_modules/payload/skills/payload/SKILL.md`.
- `cms/src/app/_payload/api.graphql.ts` is ours: the template wires only the REST catch-all, which
  answers `/api/graphql` with a 404. Keep it until the template ships a GraphQL route.
- `create-payload-app@beta` copies the template from Payload's main branch, which can be ahead of
  the packages it installs. When upgrading Payload, compare the files under `cms/src/app/_payload/`
  with `templates/blank-tanstack` at the tag of the installed version.
- The local API enforces access control. Code with no signed-in user, such as `cms/src/seed.ts`,
  passes `overrideAccess: true`; request handlers pass the request's `user` and leave it enforced.
- `npm run dev` syncs the database schema from the config. Migrations are not set up yet.

## Design and Copy
- `streamarr-ux` is the design authority: `PRINCIPLES.md` for intent and voice, `tokens/` for
  values, `branding/` for the mark and lockup. Fonts are self-hosted; the site loads no font or
  asset CDN.
- Voice is plain and calm, in sentence case. Copy states what the product does and never invents
  users, testimonials, usage numbers or benchmarks, and it does not name or compare other media
  servers.
- Use the terms in [`CONTEXT.md`](https://github.com/streamarr/streamarr-adr/blob/main/CONTEXT.md)
  from `streamarr/streamarr-adr` (read `../streamarr-adr/CONTEXT.md` when that checkout exists).
  Settled decisions are recorded there as ADRs.

## Testing
- Test behavior at the rendered component: drive it with `user-event`, find elements by role and
  label, and assert what a visitor sees and where they land.
- Tests sit beside the code as `*.test.ts(x)`, import `describe`, `it` and `expect` from `vitest`,
  and are named `it('shouldExpectedBehaviorWhenCondition', …)`.
- Inject collaborators rather than mocking first-party modules. Components that link to site paths
  render through `site/src/test/renderInRouter.tsx`.
- Tests never reach a real CMS. The CI `prerender` job is the one place the two packages meet.
